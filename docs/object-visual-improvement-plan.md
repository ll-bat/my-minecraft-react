# Object and Block Visual Improvement Plan

**Status:** Phases 1–9 are complete. The project now has a reproducible hybrid asset pipeline, shared face-aware atlases, redesigned world and inventory art, construction shapes, instanced decorative models, deterministic environmental polish, live performance diagnostics, conservative greedy meshing, and automated asset validation.

## Goal

Give the game a coherent, friendly voxel style while keeping Ultra render distance responsive. Blocks should be immediately recognizable in the world, hotbar, inventory, and catalog. Repeated world elements should remain inexpensive, while special objects can use more detailed geometry.

## Visual direction

Use a hybrid asset workflow:

- Use the downloaded Kenney Voxel Pack as source art for common terrain, building blocks, plants, fluids, ores, tools, and item icons.
- Create project-specific textures for features the pack does not contain, including copper, crystal materials, portals, powered lamps, enchanting objects, custom doors, and creature-related items.
- Use generated textures only as fallbacks for data-pack blocks and rapid prototypes.
- Build repeated construction pieces with lightweight voxel geometry generated by the chunk worker.
- Use small low-poly models only for sparse decorative objects whose silhouettes cannot be represented well by cuboids.

The first visual target is a clean 128 × 128 illustrated voxel style based on the downloaded pack. Original source assets stay unchanged under `src/images/assets/`; game-ready derivatives belong under `src/images/game/`.

## Phase 1: Establish the art contract

**Status: Complete.** The visual style guide, directory rules, stable-ID requirement, generated asset manifest, and inventory/catalog review surface are in place.

1. Define a compact project palette for soil, stone, wood, foliage, metals, water, lava, magic, highlights, and shadows.
2. Define asset conventions:
   - Block faces use square PNG files.
   - Transparent pixels use straight alpha.
   - Textures contain no baked perspective or external border unless the block design requires one.
   - Models use one world unit per block, Y-up orientation, and their origin at the center of the occupied voxel.
   - File names use stable block or item IDs.
3. Keep all existing block and item IDs so saved worlds remain compatible.
4. Add an asset manifest recording the source file, game-ready file, license, author, and whether the asset is original or modified.
5. Create a small in-game visual test area containing every texture class: opaque, cutout, translucent, emissive, fluid, and directional.

**Deliverable:** A documented visual style and asset contract that prevents later blocks from looking unrelated.

## Phase 2: Build the texture and atlas pipeline

**Status: Complete.** `npm run assets:build` produces padded power-of-two atlases and JSON UV metadata for four render layers, while retaining individual game-ready derivatives.

1. Add `src/images/game/blocks/`, `src/images/game/items/`, `src/images/game/models/`, and `src/images/game/atlases/`.
2. Keep the downloaded Kenney files as immutable sources. Copy or derive only selected files into the game-ready directories.
3. Add a repeatable atlas-building script that:
   - Reads the game-ready block textures.
   - Validates dimensions and alpha usage.
   - Adds padding around atlas cells to prevent texture bleeding.
   - Produces atlas PNG files and JSON UV metadata.
4. Build separate render atlases for:
   - Opaque blocks.
   - Alpha-cutout plants, ladders, and fences.
   - Translucent glass, windows, water, and portal effects.
   - Emissive blocks if they require different material settings.
5. Configure textures once with the correct nearest filtering, wrapping, mipmaps, and color encoding.
6. Keep a development fallback that loads an individual texture when an atlas entry is missing.

**Deliverable:** Adding a texture becomes a data change, and many block types can share a small number of GPU materials.

## Phase 3: Support different textures on each cube face

**Status: Complete.** Face fallbacks, directional rotation, worker-safe metadata, shared render-layer meshes, collision independence, and geometry regression tests are implemented.

1. Extend block visuals from one `texture` property to a face-aware definition:

```js
textures: {
    top: "grass_top",
    bottom: "dirt",
    side: "dirt_grass"
}
```

2. Support `all`, `side`, and individual `north`, `south`, `east`, and `west` overrides without requiring every face to be declared.
3. Pass only serializable atlas and face metadata to the mesh worker.
4. Update chunk mesh generation to write the correct atlas UV coordinates for each visible face.
5. Group mesh output by render layer instead of creating a separate material for every block ID.
6. Preserve current collision generation because visual face selection should not affect physics.
7. Add geometry tests for top, bottom, side, directional, transparent, and fallback face selection.

**Deliverable:** Grass, logs, crafting tables, furnaces, chests, and other directional blocks can look correct from every side without increasing draw calls for every new block.

## Phase 4: Redesign the core world blocks

**Status: First pass complete.** Existing terrain, fluids, logs, leaves, crops, ores, the crafting table, and furnace use the new art. Gravel, snow, ice, bricks, mossy and polished stone, red and pale wood, pale logs, and cactus were added to the catalog.

Replace the most common blocks first because they dominate every scene.

1. **Terrain:** dirt, grass top and side, stone, sand, gravel, snow, and ice.
2. **Nature:** log end and bark, leaves with cutout transparency, tall grass, flowers, mushrooms, cactus, and crop stages.
3. **Fluids:** cleaner water and lava surfaces, with subtle frame-based or UV animation added only after static rendering is correct.
4. **Resources:** coal, iron, copper, gold, crystal, and future ore textures sharing a consistent stone base.
5. **Building materials:** wood planks, red brick, gray brick, mossy stone, red wood, pale wood, polished stone, and colored decorative blocks.

Use Kenney art directly where it fits. Recolor or redraw derivatives for copper, crystal, obsidian, and other project-specific materials. Keep the original source files available for comparison.

**Deliverable:** Generated terrain and basic houses receive a visible quality improvement before new object types are introduced.

## Phase 5: Redesign functional blocks and inventory art

**Status: Complete.** Functional blocks now use coordinated directional atlas faces. Doors, windows, beds, lamps, portals, and enchanting blocks have purpose-built pixel art. Materials, tools, and creature items use a shared item atlas, while cube inventory entries use three-face previews from the exact world textures. The same block and item art is used for held objects and world drops.

1. Create directional face sets for the crafting table, furnace, chest, lamp, portal, and enchanting table.
2. Redraw the door and window as coordinated building pieces with matching wood, glass, hinges, and handles.
3. Improve beds with separate pillow, blanket, frame, side, and end details.
4. Use the downloaded tool and material illustrations where they match existing items; create matching original icons for missing items.
5. Replace color swatches in the inventory with actual item artwork.
6. Render block previews from the same face definitions used by the world. Directional blocks should use a consistent three-quarter preview.
7. Render model-based objects from the same model and materials used in the world, using a small reusable preview scene or cached thumbnails.

**Deliverable:** The inventory accurately communicates what every selected object will look like after placement.

## Phase 6: Add lightweight construction shapes

**Status: Complete.** A worker-safe multi-cuboid shape system now powers lower and upper slabs, directional lower and upper stairs, automatically connected wooden fences, stone walls and wooden railings, plus posts, directional beams, cuboid torches, and lanterns. Each shape has matching render and collision parts, participates in chunk-boundary neighbor rebuilding, persists its placement state, appears in the creative catalog, has an accurate inventory silhouette, and can be crafted in survival mode.

Add useful shapes before decorative models because they expand building possibilities while remaining compatible with chunk meshing.

1. Add slabs with top and bottom placement.
2. Add stairs with four directions and upper/lower orientation.
3. Add wooden and stone fences that connect to adjacent compatible blocks.
4. Add walls, posts, beams, and railings.
5. Add lanterns and improved torches using several small cuboids rather than crossed planes.
6. Define each shape as reusable cuboid parts with UV, rotation, occlusion, selection bounds, and collision bounds.
7. Rebuild neighboring chunks when a connected shape changes.

**Deliverable:** Players can build roofs, paths, balconies, fences, and detailed facades without introducing expensive standalone meshes.

## Phase 7: Add low-poly decorative objects

**Status: Complete.** The project now generates and validates twenty compact embedded glTF objects with matching previews. A cached loader shares each model asset, and active placements of the same type render through one instanced mesh. Object definitions support rotation, scale, a placement footprint, collision bounds, light emission, catalog grouping, and interaction-point metadata. The collection includes the complete furniture, storage, interior, and outdoor sets below; none are inserted into terrain generation.

Use glTF/GLB models only for sparse objects with silhouettes that cuboids cannot express well.

1. Establish a model loader with caching and shared materials.
2. Support rotation, scale, placement footprint, simple collision bounds, and interaction points in object definitions.
3. Start with a small coordinated furniture set:
   - Chair, stool, table, shelf, and cabinet.
   - Barrel, crate, basket, flowerpot, and planter.
   - Floor lamp, hanging lantern, rug, and wall decoration.
4. Add outdoor decorations:
   - Rocks, bushes, fallen logs, signs, benches, and path markers.
5. Instance repeated objects when they share model and material.
6. Keep detailed decorative objects out of terrain generation until their draw-call and memory cost is measured.

**Deliverable:** Houses and settlements can feel inhabited without turning every decorative item into a full cube.

## Phase 8: Add variation and environmental polish

**Status: Complete.** Dirt, grass, stone, sand, leaves, and every ore choose between deterministic variants using the world seed and block position. Vertex colors provide stable directional face shading, while grass, foliage, and water receive biome-aware tints. Emissive atlas materials cover lava, lamps, crystals, portals, torches, lanterns, and enchanting blocks. Water, lava, portals, and powered lamps animate through small padded-atlas offsets at eight updates per second without React state changes. The breaking indicator follows each block's cuboid or model collision shape. Fog and sunlight continue to follow biome, weather, fluid, dimension, and time-of-day state; material roughness is now selected by render layer. Expensive per-block shadow maps remain disabled to protect Ultra-distance performance.

1. Add deterministic texture variants for dirt, stone, grass, sand, leaves, and ores using the world seed and block position.
2. Add subtle per-face shade or vertex ambient occlusion so adjoining cubes have depth.
3. Add biome tinting for grass, foliage, and water without creating duplicate textures for each biome.
4. Add restrained emissive maps for lava, lamps, crystal blocks, portals, and enchanting objects.
5. Animate water, lava, portal, and powered blocks at a low update rate independent of React renders.
6. Add breaking overlays that follow the selected block shape and retain the underlying texture.
7. Review fog, sunlight, shadows, and material roughness against the new palette.

**Deliverable:** Natural areas have variation and depth while all blocks still belong to one visual style.

## Phase 9: Performance and quality validation

**Status: Complete.** The F3 overlay measures frame average and p95, draw calls, rendered triangles, Three.js geometry and texture allocations, estimated active buffer memory, worker mesh p95, mesh-install p95, render-layer triangles, and instanced-object triangles. It retains session readings for distances 2 and 4 and compares them with documented budgets. Compatible opaque full-block faces use texture-preserving greedy meshing; translucent block types remain in separate sorted batches. Automated checks cover merged geometry, atlas tile attributes, transparent separation, all shaped-object metadata and bounds, worker parity, padding, provenance, and licensing. The release checklist records the remaining browser-level visual review.

1. Measure frame time, draw calls, triangles, GPU memory, worker mesh time, and mesh-install time at render distances 2 and 4.
2. Set budgets for each render layer and object category.
3. Add greedy meshing for neighboring faces that use the same atlas entry and lighting state.
4. Keep transparent geometry separately sorted and avoid merging incompatible translucent surfaces.
5. Confirm that texture atlases do not bleed at distance or during mipmapping.
6. Test block placement, removal, collision, rotation, saving, loading, drops, and previews for every new shape.
7. Add a visual review checklist covering seams, incorrect faces, transparency, scale, clipping, z-fighting, and inventory/world mismatch.
8. Verify all third-party assets against `docs/asset-credits.md` before release.

**Deliverable:** The improved art remains smooth at Ultra distance and does not break existing worlds or interactions.

## Completion criteria

- Core blocks have intentional top, side, and bottom artwork where appropriate.
- World rendering, inventory, hotbar, drops, and catalog show matching designs.
- New construction shapes have correct selection and collision behavior.
- Decorative models use the same scale, palette, and lighting conventions as blocks.
- Third-party provenance and licenses are recorded.
- Existing saves load without block-ID migrations.
- Ultra render distance remains responsive and does not materially increase draw calls per visible block type.
